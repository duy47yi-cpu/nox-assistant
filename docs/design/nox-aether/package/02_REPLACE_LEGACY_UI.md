# AETHER / CLEAN REPLACEMENT OF LEGACY UI

## Решение владельца

**Уйти от прежнего визуального интерфейса, не строить сверху него.** После выбора концепции создать **отдельную новую оболочку UI**, которой не передаются старые каскады CSS/DOM. При этом не удалить вместе с оформлением работу агентных инструментов, историю, голос, approvals и две готовые сферы.

«Удалить» в дизайне и «удалить рабочий код» — разные действия. Новую оболочку нужно сделать действительно новой. Legacy допускается лишь как временная безопасная точка отката во время миграции; после успешной приёмки и разрешения владельца legacy можно убрать.

## Исходная ситуация: реальная карта Nox

Из предоставленного `AGENTS.md` (проверить актуальный git status перед работой):
- `renderer/index.html` — разметка окна.
- `renderer/app.js` — сообщения, инструменты, состояния чата, команды.
- `renderer/nox-screen.js` и `renderer/nox-screen.css` — текущая композиция Nox.
- `renderer/nox-shell.css`, `renderer/presence.css`, `renderer/themes.css` — разные каскады оформления.
- `renderer/orb.js`, `renderer/orb-variants.js`, `renderer/orb-nox.js`, `renderer/orb-tune.js` — сферы/их виды/настройки.
- `renderer/shared.js` — подписи и статусы.
- `main.js` / `preload.js` — IPC, backend и доступы. **Не переписывать из-за внешнего вида.**

Это ориентиры, а не разрешение всё заменить. Подозрительные исходники и текущие незакоммиченные изменения сначала инвентаризировать.

## Запрет «CSS-пластыря»

**НЕЛЬЗЯ:**
- Просто добавить `aether.css` последним и переопределить сотни селекторов старых тем.
- Накрыть старый чат непрозрачной панелью, оставив старые интерактивные элементы с фокусом/событиями.
- Наложить второй composer/область сообщений поверх первого.
- Сохранить две видимые/невидимые активные системы approvals или двойную подписку на agent:event.
- Скрывать старые компоненты только `z-index`/`opacity` без удаления из tab order и событий.
- Заставлять существующую сферу рендериться дважды одновременно.

## Правильный путь

### Период A — до выбора дизайна
Только изолированные макеты/прототипы, без изменения реального Nox. Снимки старого UI и две сферы фиксируются как контрольные эталоны.

### Период B — реализация новой оболочки (после выбора)
1. Выделить **ограниченный контракт UI ↔ модель состояния**: история, сообщение, поток, инструменты, approvals, voice, setting change, stop/error. Изучить текущую маршрутизацию событий, не дублировать её.
2. Создать отдельный **Aether root** и отдельный набор токенов/стилей, изолированных от legacy. Реализация может быть новой страницей или отдельно монтируемым корнем; выбор обосновать после изучения кода.
3. Перенести **представление**, а не переписать backend: реальные действия вызывают имеющиеся проверенные API, никогда собственные обходные вызовы.
4. Для сфер использовать adapters, которые монтируют **одобренные оригинальные рендереры** через registry. Внутренние модули двух оригиналов не изменять.
5. Для legacy сделать явный переключатель `uiVersion` только на время теста. При активном Aether **не импортировать старые листы оформления чата** в его корень. Не подключать их глобальные селекторы, если они влияют на Aether.
6. Тестом доказать, что в Aether отсутствуют два composer, две истории, двойные event listeners и двойной Canvas.
7. Подключить окна, accessibility, тему, масштаб и голос в соответствии с уже существующим API.

### Период C — замена по умолчанию
- После тестов Haiku/Opus и одобрения владельца переключить главную точку входа на Aether.
- Оставить legacy невидимым и неактивным **только как временный rollback**, если это необходимо для стабильности.
- Не сохранять бесконечную поддержку обоих UI по умолчанию.
- На отдельном шаге инвентаризировать возможность физического удаления устаревшей разметки/стилей, показать безопасный diff, удалить **только после согласования** и полного регресса.

## Контракт совместимости и запреты

- Не менять значения разрешений, внутренние approval identifiers, policy/taint, аргументы инструментов.
- Не терять историю чатов, ссылки на источники и возможность копирования.
- Не пересоздавать модель агента/подписки во время смены темы/сферы.
- Не переносить пользовательские данные из `data/` ради тестов; использовать временные профили.
- Не дублировать IPC и не выдавать renderer новые привилегии.
- Не делать состояние UI источником права на выполнение команды.
- Не менять файлы C5/C6/C7.

## Технические требования к отключению старого UI

Acceptance checks:
- `Aether` загружается без старой визуальной сетки, лишних рамок и глобальных override из legacy.
- Старый UI не виден, не доступен фокусом, не получает pointer/keyboard events, не держит активные таймеры/рендеринг.
- Функции не деградируют: send, stream, stop, tool cards, approvals, history, voice, settings, window controls.
- Переключение в rollback (только тест) не теряет данные.
- При закрытии/открытии приложения Aether остаётся выбранным в тестовом профиле.
- При повреждённом пресете внешний вид восстанавливается без потери настроек агента.
- `project-map.test.js` выполняется после добавления новых файлов, `AGENTS.md` обновляется согласованно.

## Владелец файлов

Fable — новый Aether UI и его тесты после выбора. Opus — решение о границах интеграции, QA и архитектурные решения; Haiku — read-only проверка/снимки. Если конфликт в `renderer/index.html`/`app.js` с другими агентами, не редактировать до согласования файла. Никогда не перезаписывать незакоммиченный diff чужого агента.
