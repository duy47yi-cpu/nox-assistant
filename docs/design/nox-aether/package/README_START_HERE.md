# NOX AETHER — START HERE

**Назначение:** пакет для запуска **новой сессии** разработки нового визуального интерфейса Nox Assistant. Версия ТЗ: 2026-11-13.

## Главное решение владельца

- Нынешний чат **не устраивает**. Нужен новый, более красивый и удобный интерфейс — **не надстройка из CSS поверх старого**.
- Не делать корпоративный дашборд: никаких постоянных панелей с метриками, отчётами, пятью колонками и декоративным шумом.
- Сохранить две хорошие существующие сферы — **«точечную» и «синюю»** — без изменений в их движке/внешности. Проверить в проекте, какие модули и настройки им соответствуют; не угадывать по названию. Перенести/доступно подключить их через **библиотеку сфер («инвентарь»)**. В дальнейшем сфер может быть сколько угодно.
- Пользователь сам настраивает чат, расположение панелей, сферы, темы, шрифты, фоны и движения в «Мастерской Nox».
- Изучить четыре прикреплённые фотографии: две версии Nox и две версии Jarvis Pro. Jarvis Pro — **референс композиции, не объект для копирования**.
- **Opus 5.5** — ведущий и координатор, **Fable 5.2 Medium** — основной дизайнер/реализатор, **Haiku 5.5** — независимый QA. Делегирование только если платформа реально поддерживает создание субагентов; не придумывать результаты.
- Каждый агент **постоянно фиксирует сделанное, изменённые файлы, проверки и следующее действие**, чтобы работу можно было передать другому при лимите модели.

## Содержимое пакета

1. `NOX_AETHER_VISUAL_BRIEF.pdf` — обзор со всеми 4 исходными фотографиями, ограничениями и планом.
2. `00_OPUS_MASTER_PROMPT.md` — **основной промпт**, который нужно отправить Opus в новой сессии.
3. `01_VISUAL_DESIGN_SPEC.md` — дизайн-система, чат, сфера, референсы, кастомизация, ключевые сценарии.
4. `02_REPLACE_LEGACY_UI.md` — безопасная стратегия **замены** старого UI, а не перекрытия новыми стилями.
5. `03_ORB_INVENTORY_AND_CUSTOMIZATION.md` — сохранение двух оригинальных сфер, реестр вариантов, Мастерская Nox.
6. `04_TEAM_DELEGATION.md` — распределение задач между Opus / Fable / Haiku и экономия стоимости.
7. `05_PROGRESS_AND_HANDOFF.md` — строгий протокол журналов, чекпойнтов, передач сессии и образцы.
8. `06_TESTS_AND_ACCEPTANCE.md` — обязательные проверки, режимы окна, критерии приёмки.
9. `07_REFERENCE_MAP.md` — что означает каждая фотография и какие детали считать важными.
10. `assets/` — четыре исходных пользовательских скриншота.
11. `agent-logs/` — шаблоны рабочих журналов; в реальном проекте агенты должны создать свои журналы в согласованной отдельной папке.

## Как использовать

**Новая сессия:** приложить PDF и этот ZIP либо отдельные MD-файлы; вставить текст `00_OPUS_MASTER_PROMPT.md`. Сообщить агенту, что **файлы — нормативные требования, а изображения — ориентиры**, и нужно сохранять реальные функции приложения.

**Этап 1:** Opus изучает текущий код, делегирует Fable подготовку **трёх действительно разных макетов и изолированных прототипов**. Haiku проверяет. Показывают владельцу: обычный диалог, длинный ответ, работу агента, подтверждение, «Мастерскую Nox».

**Остановка 1:** **никаких изменений в боевом UI до выбора концепции владельцем.**

**Этап 2 после выбора:** Fable строит новую отдельную оболочку (UI v2), соединяет её с существующими данными/инструментами, проверяет в реальном Electron, Haiku проводит QA, Opus принимает.

**Остановка 2:** старый UI остаётся доступным как **временный fallback** лишь на период проверок. После отдельной приёмки владельцем его можно убрать без уничтожения функциональности.

**Нельзя:** трогать ветки C5/C6/C7, ломать сферы, менять политику подтверждений, удалять чужие незакоммиченные изменения, делать commit/push, устанавливать зависимости без согласия, читать настоящие `.env`/`data/`.
