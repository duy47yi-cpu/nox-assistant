# AETHER / OPUS → FABLE → HAIKU DELEGATION PROTOCOL

## Модель стоимости

**Opus 5.5** — дизайн-директор, не «самый дорогой фронтенд-исполнитель». Решает архитектурные узлы, расставляет приоритеты, ставит точные задачи и оценивает. **Fable 5.2 Medium** — основной создатель макетов и реализации. **Haiku 5.5** — независимый QA, быстрые проверки, не полноценный второй дизайнер. Никакой модели не нужно многократно читать все 74 видео без узкой причины.

Если инструментов для вызова конкретной модели нет, Opus создаёт `FABLE_TASK.md` и `HAIKU_TASK.md` с готовыми контекстом, входами, выходами, а владелец передаёт их в отдельные сессии. Нельзя заявлять, что субагент работал, если этого не было.

## Распределение полномочий

| Агент | Отвечает | Не делает |
|---|---|---|
| Opus | Анализ проекта, визуальные стандарты, дизайн-гейты, архитектура миграции, выбор точек интеграции, конфликт-менеджмент | Повторять типовые CSS-правки, выдавать собственные фантазии за отчёт Fable/Haiku |
| Fable | 3 макета, прототипы, отдельный Aether UI после approval, UI компоненты, доступность, темы и инвентарь сфер | Менять safety policy, C5/C6/C7, оригинальные сферы, создавать новое «поверх» legacy |
| Haiku | Независимая сверка спецификации, реальные screenshots QA, broken states, responsive, keyboard, reduced motion, регрессии и report | Переписывать весь UI, подтверждать ошибки без воспроизведения, менять файлы Fable без разрешения |

## Обязательные tickets

### Ticket D0 / Opus — Baseline
**Вход:** README/MD/PDF, 4 screenshots, `AGENTS.md`, актуальный код. **Выход:** перечень UI entrypoints, карта CSS conflicts, список двух точных оригинальных сфер, контракт событий чата, список файлов занятых агентами. **Gate:** согласованы границы новой оболочки и изоляция макетов.

### Ticket D1 / Fable — 3 визуальных направления
**Вход:** `01_VISUAL_DESIGN_SPEC.md`, `07_REFERENCE_MAP.md`, baseline D0. **Выход:** A Minimal Presence, B Fluid Workspace, C Spatial Dialogue; каждая с фиксированным одинаковым контентом, снимками 1200×720 и 864×520, один mock рабочего чата, один состояния выполнения, «Мастерская Nox». **Gate:** никаких корпоративных панелей KPI или копирования Jarvis Pro.

### Ticket Q1 / Haiku — Design QA
**Вход:** D1 renders и бриф. **Выход:** для каждого варианта точные замечания с координатой/путём и предложением исправления, pass/fail на читаемость и различие концепций. **Gate:** до двух итераций.

### Ticket A1 / Opus — Selection review
**Вход:** D1+Q1. **Выход:** рекомендация и сравнение с референсами, компромиссы, 3 готовые картинки/прототипы владельцу. **СТОП:** получить выбор от владельца.

### Ticket I1 / Fable — Aether shell после выбора
**Вход:** одобренная концепция, `02_REPLACE_LEGACY_UI.md`, baseline. **Выход:** отдельный root/stylesheet, no legacy overlay, сохранены функции чата/approvals/voice, флаг UI v2 только для тестового профиля. **Gate:** отсутствие двойных listeners и CSS leakage.

### Ticket I2 / Fable — Orb inventory + Workshop
**Вход:** I1, `03_ORB_INVENTORY_AND_CUSTOMIZATION.md`. **Выход:** точечная и синяя original в библиотеке с оригинальной реализацией; пользовательские пресеты, безопасный импорт/экспорт, настройки без CSS/JS. **Gate:** визуальная проверка baseline двух оригиналов.

### Ticket Q2 / Haiku — Real Electron QA
**Вход:** I1+I2. **Выход:** независимые снимки 1200×720 / 864×520 / 1440×900, keyboard, long conversation, tool approvals, content redaction, renderer console, viewport overflow, performance hints. **Gate:** баги с severity и repro.

### Ticket A2 / Opus — Feature acceptance
**Вход:** all outputs, test logs, risk register. **Выход:** GO/NO-GO для owner QA. **СТОП:** до owner acceptance не менять default и не удалять legacy.

## Правила экономии

- Декомпозировать задачу до проверяемого ticket (вход / выход / acceptance / разрешённые файлы), а не каждый раз пересылать тысячи строк истории.
- Fable и Haiku не редактируют одни файлы параллельно; Haiku ведёт собственный лог и наблюдения.
- Opus использует краткие summaries, диффы и screenshots, а не полные повторные аудиты.
- Каждая заметная архитектурная смена фиксируется в `OPUS_DECISIONS.md` один раз.
- Не допускать бесконечного циклa «критика → новый полный редизайн». Максимум две итерации Fable → Haiku; далее выбор владельца.
- При отсутствии явных source bounds модель отвечает «не проверял» — не придумывает.

## Договорённость по тестам

При одновременной работе C5/C6/C7 не запускать несколько тяжёлых Electron/capture/end-to-end suite параллельно. Fable/Haiku сначала запускают только целевые тесты/локальные mock views, полный прогон после согласования окна с другими агентами. При чужом красном тесте зафиксировать baseline и не трогать несвою область.
