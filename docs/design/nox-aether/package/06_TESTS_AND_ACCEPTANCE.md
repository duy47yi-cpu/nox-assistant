# AETHER / QA AND ACCEPTANCE CONTRACT

## Gate 1 — три концепции, до изменения кода Nox

- [ ] Три действительно разные композиции, а не одна сетка с другой темой.
- [ ] Все 3 показывают одинаковые тестовые сообщения: пустой экран, короткий диалог, длинный markdown, код/таблица, 8+ инструментов, одно подтверждение, голос.
- [ ] Сфера доминирует в пустом состоянии и не мешает читать длинные ответы.
- [ ] Нет корпоративного дашборда, гигантских отчётов/метрик в постоянном правом sidebar.
- [ ] Каждая концепция представлена при 1200×720 и 864×520.
- [ ] Продумана «Мастерская Nox» с выбором двух исходных сфер.
- [ ] Есть критическая проверка Haiku и не больше двух циклов исправлений.
- [ ] Владелец увидел варианты и **выбрал один** перед реализацией.

## Gate 2 — новая оболочка, не оверлей

- [ ] Aether root не импортирует без необходимости legacy CSS, не зависит от общего слоя стилей старого чата.
- [ ] Нет двух одновременно активных чатов/composer/history, двойных IPC subscriptions/approval controls/Canvas.
- [ ] При старте UI v2 — именно новый layout, без старых сеток/пустых границ/перекрытых панелей.
- [ ] История, файлы, источники, Markdown, ссылки, copy, отправка, стриминг, стоп, errors и approvals функционально эквивалентны.
- [ ] Миграция настроек версионирована и не теряет пользовательские данные.
- [ ] Состояние событий агента отображается честно; не меняет access policies.
- [ ] Режим fallback изолирован и недоступен обычным пользователям после окончательной приёмки.

## Gate 3 — визуальные и функциональные проверки

### Матрица окон

| Сценарий | 1200×720 | 864×520 | 1440×900 |
|---|---|---|---|
| Пустой чат и сфера | Screenshot | Screenshot | Screenshot |
| Длинный ответ (RU/EN) | Layout | Overflow | Readability |
| Код и таблица | Scroll | Scroll | Interaction |
| 8+ инструментов | Compact | Compact | Expand |
| Confirm dialog | Visible | Fully visible | Keyboard |
| Ввод 10 строк | No clipping | No clipping | No clipping |
| Настройки / инвентарь сфер | No overlap | Scrollable | Preview |
| Voice/disabled/error/stop | Truthful | Truthful | Truthful |

### Оригинальные сферы

- [ ] В инвентаре присутствуют **точечная** и **синяя**, точно сопоставленные с реальным кодом.
- [ ] Проверен исходный и новый внешний вид одного варианта при одинаковом размере/настройках.
- [ ] Без изменений в оригинальных shaders/Canvas/WebGL реализациях.
- [ ] Смена A↔B освобождает старый контекст, не создаёт второй рендер.
- [ ] Сворачивание окна приостанавливает работу; возвращение восстанавливает.
- [ ] Настройки других сфер не меняют baseline originals.

### Анимации и доступность

- [ ] Windows reduced motion соблюдается; движения не мешают работе.
- [ ] Фокус клавиатуры последовательный; Enter/Esc соответствуют действующим правилам.
- [ ] Цветные статусы имеют текстовое отличие; «ожидает подтверждения» не спутать с «успех».
- [ ] Контраст читаемого текста и кнопок проходит обоснованную проверку.
- [ ] Скролл длинных переписок стабилен при streaming и новых ответах.
- [ ] При изменении размера окна не появляется бесконечная горизонтальная прокрутка страницы.
- [ ] Меню и модальные окна не уходят за пределы 864×520.

### Производительность / безопасность

- [ ] Тяжёлая сцена не тормозит ввод текста и streaming.
- [ ] Не рендерить скрытую сферу, если пользователь выбрал «Скрыть».
- [ ] Реальное измерение анимации/FPS/загрузки, без неподтверждённых маркетинговых цифр.
- [ ] Импорт пресета валидирует значения, не исполняет произвольный CSS/JS.
- [ ] Пресеты не влияют на mode, approvals, C5/C6/C7, IPC permissions, токены.
- [ ] Пользовательский фон обрабатывается локально, не отправляется в сеть.
- [ ] Прототип не читает настоящие данные пользователя.

## Автотесты и живое приложение

Из карты `AGENTS.md` известны сценарии `scripts/nox-shot.js`, `scripts/nox-qa-verify.js`, `scripts/nox-screens-shot.js`, `tests/project-map.test.js` и общий `node --test`. **Сначала убедиться в существовании и актуальности команд**, никогда не предполагать, что старый сценарий автоматически подходит новому UI. Создать/адаптировать целевые тесты Aether после выбора концепции. Тяжёлые тесты запускать согласованно, чтобы не маскировать флуктуации параллельных процессов C5/C6/C7.

## Как оформить QA

Каждый найденный дефект: severity (`P0` broken action/security, `P1` blocked core function, `P2` significant visual/UX, `P3` polish), точное окно и шаги, ожидаемое/фактическое, screenshot или тест, ответственный агент, статус. **PASS** — только после воспроизведения исправленного сценария, не на основании слов исполнителя.

## Признаки провала проекта

- Красивый CSS поверх старого layout.
- Две оригинальные сферы перерисованы/заменены без разрешения.
- Постоянный KPI dashboard вместо персонального ассистента.
- Нельзя прочитать длинный ответ на 864×520.
- Действия / подтверждения стали красивыми, но неправильными.
- Нет реальных визуальных сравнений и независимой проверки.
- Агент остановился и не оставил HANDOFF.

## Когда сказать владельцу «готово»

Только после его выбора и прохождения Gate 2/3. Релизный «готово» не означает, что автономная безопасность или вся C5/C6/C7 приняты; это отдельные компоненты.
