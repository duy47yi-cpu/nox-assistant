# Автономный Джарвис: исследование и план

Дата: 2026-11-04. Автор: ведущий агент (Team Lead). Только чтение кода и внешние источники; ничего в приложении не менялось.

## 0. Коротко

- **Руки и глаза — уже не главный дефицит.** В проекте есть UI Automation, снимок экрана, OCR, браузер, файлы, установка программ, голос. Живой сценарий «сохранить файл через модель» уже проходит (см. `.megapowers/run/computer-use-20261104/`).
- **Главный дефицит — автономный контур:** единое восприятие сцены, память-петля, навыки из опыта, движок целей «план → действие → проверка → перепланирование».
- **Надёжный рецепт из исследований:** гибрид «дерево доступности (UIA) + снимок + OCR + DOM», адресация элементов устойчивыми id, проверка каждого шага, разделение планировщика и исполнителя, риск-гейт вместо тотальных подтверждений.
- **Память:** не «векторный склад», а петля «записать → прочитать → обновить → забыть». Для одного пользователя файлы/JSONL часто лучше графовой БД; при меняющихся фактах нужны сроки действия (temporal validity).
- **Обучение:** библиотека исполняемых процедур (как Voyager), а не только текстовые инструкции. Успешный ход → процедура с предусловиями, шагами и проверкой → повторное использование.
- **Безопасность:** полная автономия без ограничения прав — риск потери данных и утечек. Нужны мандаты на задачу, метки «недоверенного текста», эгресс-контроль, аудит и аварийный стоп.

Чего нет как системы:

1. **Единого наблюдения.** Модель вызывает `ui_windows`, потом `ui_elements`, потом `screen_look`; каждый инструмент возвращает свой кусок, между вызовами сцена меняется, а сравнения «что изменилось» нет.
2. **Автоматической памяти.** Модель должна сама догадаться вызвать `remember`. После хода не извлекаются факты, эпизоды, процедуры; противоречия не разрешаются.
3. **Обучения.** Навык — текст, который модель читает. Успешная последовательность действий не превращается в повторяемую процедуру.
4. **Движка целей.** Есть «долгое поручение» и «миссия», но нет общего объекта «цель → план → шаги → проверка → перепланирование» с бюджетом и эскалацией.
5. **Единого восприятия и действий по id.** Действия ищут элемент по подписи каждый раз; нет стабильного id, предусловий, проверки «до/после», отката.
6. **Защиты от недоверенного текста.** Веб-страница, файл или письмо могут подтолкнуть модель к действию; меток происхождения и запрета на повышение прав нет.

## 2. Что говорит исследование

### 2.1. Компьютерные агенты: гибрид, а не «только зрение»

- **Windows Agent Arena** (NeurIPS 2024): агент решает 19,5% задач против 74,5% у человека. Это не «почти готово», а разрыв в 4 раза: длинные задачи на реальном Windows всё ещё трудны.
- **macOSWorld** (2025): проприетарные агенты выше 30%, открытые — заметно ниже. Разрыв между демо и продакшеном большой.
- **OSWorld 2.0** (arXiv 2606.29537) и **StateAct** (arXiv 2607.22798) смещают оценку с «финального клика» на длинную траекторию и состояние программы. Вывод для Nox: проверять нужно не «модель сказала, что сделала», а состояние системы после шага.
- **Microsoft UFO/UFO2** (arXiv 2504.14603, «Desktop AgentOS»): Windows-агент, который комбинирует UI Automation и зрение, с центральным диспетчером. Это ближайший к Nox аналог; полезно смотреть на их разделение «наблюдение → выбор элемента → действие → проверка».
- **Agent-S** (ICLR 2025): дерево доступности с целочисленными метками, по которым модель выбирает элемент. Дешёвый и точный способ дать модели «глаза» без vision-модели.
- **UI-TARS** (arXiv 2501.12326) и **UI-TARS-2** (2509.02544): сквозные GUI-агенты, обученные на траекториях; **OmniParser**: разбор снимка на элементы, когда UIA недоступен (Electron, игры, удалённый рабочий стол).
- **ScreenSpot-Pro** (2025): grounding на высоком разрешении — отдельная трудная задача; координаты «на глаз» на 4K/масштабе 150% часто врут.
- **Simular, «The Autonomous Computer»** (YouTube, транскрипт): три сигнала — снимок, дерево доступности, DOM; сначала агент писал код как политику с проверкой каждого запуска, затем перешёл к гибриду; менеджер/воркеры; библиотека навыков. Важная мысль: «код как политика + верификация» даёт детерминизм там, где повторяющаяся задача.

**Что это значит для Nox.** Не заменять UIA на vision и не заменять vision на UIA. Нужен один снимок сцены, где есть:
- активное окно и фокус;
- плоское дерево элементов с устойчивыми id (UIA name/type/automationId + границы);
- снимок экрана (для мест, где UIA слеп: Chrome, Electron, MMC, игры);
- OCR-текст и, если открыт браузер, URL/заголовок/DOM-срез;
- дельта к прошлому шагу.

### 2.2. Память: петля, а не склад

- **MemGPT/Letta** (arXiv 2310.08560): «операционная система памяти» — небольшая core-память в промпте + архив, модель сама решает, что записать и что достать. По обзорам, Letta-подобные архитектуры — одни из сильнейших на LongMemEval (около 83%).
- **Mem0** (arXiv 2504.19413): слой извлечения фактов из диалога; быстрый старт, но разрешение противоречий зависит от модели, истории версий нет.
- **Zep/Graphiti** (arXiv 2501.13956): временной граф знаний; у факта есть срок действия, новый факт вытесняет старый. Это прямо решает проблему «клиент женился, а ассистент полгода пишет „холост“».
- **Обзоры памяти** (ACM TOIS 2025; arXiv 2512.13564): память делят на рабочую, эпизодическую, семантическую, процедурную. Для агента важны не только факты, но и «что было» (эпизоды) и «как делать» (процедуры).
- **Практика:** векторная память без времени деградирует после нескольких сотен записей, старые и новые версии факта соседствуют. Забывание — функция, а не баг. Для одного пользователя Markdown/JSONL + аккуратная схема часто лучше «настоящей» БД: видно, что помнит агент, легко отладить.

**Что это значит для Nox.** Текущая память — хороший фундамент (профиль, сроки, чувствительное, stemming). Не хватает:
1. записи после хода: извлечь 0–3 факта/эпизода, оценить важность, проверить на секреты;
2. обновления: новый факт с тем же субъектом/предикатом вытесняет старый, старый получает `validUntil`;
3. эпизодов: краткая запись «что просили, что сделали, чем подтвердили» для долгих задач;
4. консолидации: раз в сутки сжать дубли, удалить просроченное, поднять важное;
5. видимого интерфейса памяти (просмотр, правка, удаление) — доверие к «второму мозгу» без этого невозможно.

### 2.3. Обучение: исполняемые навыки

- **Voyager** (arXiv 2305.16291): библиотека навыков как исполняемого кода; агент добавляет навык после успешной задачи и комбинирует их в новых мирах. Это самый сильный известный рецепт «учиться на опыте» для агента.
- **Self-improving agents** (обзоры 2025–2026; ACL 2026 «Reinforcement learning for self-improving agent with skill library»): навык должен иметь предусловия, эффекты и проверку, иначе библиотека превращается в свалку.
- **Reflexion/reflection** (YouTube-обзоры, papers 2023–2026): после неудачи полезно записать «почему не вышло» и правило на будущее; без проверки это Produces красивые, но бесполезные самоописания.

**Что это значит для Nox.** Навык должен быть не `SKILL.md` с советами, а объектом:
```json
{
  "name": "save_notepad_file",
  "when": "надо сохранить новый текст в файл через Блокнот",
  "preconditions": ["открыт Блокнот", "есть путь"],
  "steps": [{"tool": "ui_keys", "args": {"keys": "ctrl+s"}}, ...],
  "verify": {"tool": "workspace_read", "args": {"path": "{{path}}"}},
  "rollback": "удалить созданный файл, если он новый",
  "version": 1,
  "successCount": 0,
  "lastVerified": null
}
```
Успешная траектория → черновик навыка → проверка на следующей задаче → повышение версии. Провал → понижение/пометка. Владелец может посмотреть и отредактировать.

### 2.4. Автономия: план, исполнитель, проверяющий

- Длинные задачи проваливаются не из-за одного плохого шага, а из-за накопления ошибок. Нужен отдельный **verifier**, который смотрит на состояние, а не на текст модели.
- **StateAct** и OSWorld 2.0: полезно опираться на состояние программы (файл, URL, заголовок окна, запись в БД), а не только на пиксели.
- **Simular**: менеджер/воркеры и «код как политика»; повторяющиеся шаги лучше исполнять детерминированно, а модель звать на развилках.
- **Human oversight** (arXiv 2604.04918): три стратегии — подтверждать каждое действие, риск-гейт (автономно, но эскалация на опасном), супервизорное соисполнение. Для продукта правильна вторая: не спрашивать на каждый клик, но останавливать перед необратимым.

**Что это значит для Nox.** Есть `long.js` с блоками и записками — это хорошая основа. Не хватает:
- явного плана (шаги, зависимости, критерии);
- бюджета (деньги, время, число шагов) и остановки при исчерпании;
- перепланирования после неудачи (не просто «3 ошибки подряд → стоп»);
- эскалации: «нужно решение владельца» с понятным вопросом и вариантами;
- отчёта «что проверено, чем подтверждено, что осталось»;
- расписания и триггеров (время, новый файл, письмо, событие).

### 2.5. Безопасность: автономия увеличивает цену ошибки

- **InjecAgent** (ACL 2024) и адаптивные атаки (NAACL 2025): косвенные инъекции в веб-страницах/письмах/файлах обходят многие защиты. Для агента с руками это путь к «прочитал секрет → отправил наружу» или «удалил папку».
- **Least privilege / capability**: у задачи должен быть мандат: какие инструменты, папки, хосты, сколько денег, до какого времени. Вне мандата — отказ, а не вопрос посреди ночи.
- **Taint tracking**: текст со страницы/файла/письма помечается как недоверенный; действие, инициированное им (отправка, запись в автозагрузку, смена настроек), требует подтверждения или запрещено.
- **Эгресс-контроль**: исходящие адреса и домены; секреты не попадают в URL/логи; запрет на чтение `.env`, `data/`, ключей даже в полном доступе.
- **Аудит и стоп**: журнал каждого действия с предусловием/результатом; аварийный стоп (Esc уже есть) и «стоп всё» из трея/телефона.

### 2.6. Продукт и интерфейс

- Открытые «JARVIS»-проекты (YouTube: «I Built My Own JARVIS», «ClawdBot», Open Interpreter) чаще всего — чат + запуск программ + голос. Они выигрывают демо, но проигрывают на длинных задачах и доверии.
- Для «второго мозга» важнее не вау-эффект, а **прозрачность**: что запомнил, почему сделал, что собирается сделать, как отменить.
- Для «учителя» — режим объяснения: после действия короткое «почему так», уроки, проверка понимания, повторение. Это можно сделать без новой модели, на промпте и памяти.

## 4. Целевая архитектура

```
Цель владельца
   │
   ▼
goal/ (план, шаги, бюджет, срок, критерий)
   │  планировщик (умная модель, редко)
   ▼
agent/loop (исполнитель, быстрая модель)
   │  observe() ──► perception/ (UIA + screenshot + OCR + DOM, дельта)
   │  act()     ──► action/ (по id, предусловия, идемпотентность)
   │  verify()  ──► effects/ (состояние, а не слова модели)
   ▼
memory/ (факты, эпизоды, процедуры, профиль; запись/чтение/обновление/забывание)
   │
skills/ (исполняемые процедуры, версии, повтор)
   │
safety/ (мандат, taint, эгресс, аудит, стоп)
   │
interface/ (чат, голос, баннер, память, подтверждения)
```

Ключевые новые модули (предложение, не реализовано):

- `src/perception/scene.js` — `observe({window, depth, includeScreenshot, includeDom})`; возвращает компактный JSON с id, ролями, границами, фокусом, дельтой, redaction секретов.
- `src/action/element.js` — действия по `elementId`; перед действием проверяет, что элемент ещё тот; после — снимает дельту; при несовпадении — повторное наблюдение, а не слепой повтор.
- `src/memory/extract.js` — после хода: кандидаты фактов/эпизодов, важность, конфликт, запись.
- `src/memory/consolidate.js` — ночная сборка: дубли, сроки, сводка дня.
- `src/skills/procedure.js` — схема, валидатор, запуск, версии.
- `src/skills/learn.js` — траектория → черновик процедуры (только после подтверждённой проверки).
- `src/goals/engine.js` — состояние цели, план, шаги, бюджет, эскалация, перепланирование.
- `src/goals/planner.js` / `verifier.js` — отдельные роли, чтобы не смешивать «придумать» и «проверить».
- `src/safety/mandate.js` / `taint.js` / `egress.js` — мандат, метки, исходящие.

## 5. Дорожная карта

Оценки — для одного разработчика с текущим темпом; тесты и живая проверка обязательны на каждом этапе.

### Этап 0. База (идёт сейчас, другой заход)
- UIA-руки, снимок, Esc, баннер, установка с подтверждением, живой сценарий сохранения файла.
- Критерий: 1107/1107 приложение, 16/16 сервер, живой сценарий.

### Этап 1. Восприятие и действия по id (3–5 дней)
- `observe()`: активное окно, фокус, плоское дерево с id, снимок, OCR, дельта.
- `elementId` в `ui_*`: действие по id, проверка «элемент тот же», дельта после.
- Тесты: сцена меняется между шагами; элемент исчез; высокий DPI; Electron/Chrome fallback на снимок.
- Критерий: сценарий «Проводник → папка → Блокнот → текст → сохранить» проходит по id, без поиска по подписи на каждом шаге.

### Этап 2. Память-петля (1–2 недели)
- Схема: `fact` (subject, predicate, object, validFrom/validUntil), `episode` (goal, actions, outcome, evidence), `procedure` (ссылка на навык), `profile`.
- Автозапись после хода (дешёвая модель): 0–3 записи, проверка секретов, важность.
- Конфликты: новый факт вытесняет старый; старый не удаляется, а закрывается сроком.
- Консолидация раз в сутки; лимит токенов на подмешивание; UI «что я помню».
- Тесты: противоречие, срок, секрет, чувствительное, пустой ход.
- Критерий: через 10 ходов ассистент сам помнит имя, проект и договорённость; старый факт не выдаётся как текущий.

### Этап 3. Навыки из опыта (1–2 недели)
- Трассировка успешного хода: инструменты, аргументы, проверки.
- Черновик процедуры: предусловия, шаги с шаблонами, verify, rollback.
- Повтор: сначала в песочнице/на тестовой папке, затем на реальной задаче; счётчик успехов/провалов.
- Тесты: повтор процедуры после перезапуска; изменился путь — предусловие не выполнено — отказ, а не слепой повтор.
- Критерий: вторая похожая задача решается быстрее и без модели на каждый шаг.

### Этап 4. Движок целей и автономный режим (2–3 недели)
- Цель: текст, критерий, бюджет (деньги/время/шаги), срок, мандат.
- План → шаги → проверка → перепланирование; отдельный verifier.
- Эскалация: вопрос владельцу с вариантами; ожидание; продолжение.
- Расписание/триггеры; отчёт и дневная сводка.
- Автономный режим: риск-гейт (T0/T1 автономно, T2 — по мандату, T3/оплата/удаление — подтверждение), стоп.
- Критерий: задача «найди 20 вакансий, сохрани в таблицу, пришли отчёт» выполняется без участия, с проверкой каждой записи; при сбое — понятный отчёт.

### Этап 5. Безопасность (1 неделя, параллельно)
- Запрет чтения/записи `.env`, `data/`, `.git`, ключей — даже в полном доступе.
- Эгресс-контроль для `web_fetch`, `browser_*`, `shell_run`; запрет секретов в URL.
- Taint: страница/письмо/файл — недоверенные; действие по ним — подтверждение/запрет.
- Мандат на задачу; аудит; «стоп всё».
- Тесты: попытка прочитать `.env`, отправить секрет, выполнить `iwr` склейкой, выйти за мандат.
- Критерий: красная команда не проходит; легитимная задача не страдает.

### Этап 6. Голос и интерфейс (1 неделя)
- Wake word (локально), потоковая диктовка, прерывание, TTS.
- Экран памяти, история целей, «почему так», отмена.
- Критерий: «Джарвис, …» без клика; видно, что он делает и как остановить.

**Итого:** 6–8 недель сфокусированной работы. Первые три шага (восприятие, память, навыки) дают наибольший эффект для «второго мозга»; движок целей — для «полной автоматизации».

## 6. Что делать первым

1. **Дождаться/принять текущий заход computer-use** и зафиксировать базу (тесты, живой сценарий). Не начинать память и цели, пока `main.js`/`ui.js` активно правятся: конфликты дороже.
2. **Сделать `observe()` и трассу шага.** Без единого наблюдения и дельты остальное будет строиться на песке. Это же даст материал для обучения навыков.
3. **Память-петля + эпизоды.** После каждого хода — запись; раз в сутки — консолидация; UI памяти. Это «второй мозг».
4. **Навыки из успешных трасс.** Только после того, как есть проверенный `observe()` и `verify()`.
5. **Движок целей.** Собирает всё вместе; начинать с узкого класса задач (файлы/браузер/офис), не «сразу всё».

## 7. Риски и как их снижать

| Риск | Почему | Снижение |
|---|---|---|
| Потеря данных | Полные руки + ошибка модели | Мандат, подтверждение необратимого, корзина/бэкап, откат |
| Утечка секретов | Чтение `.env`, эгресс | Запрет путей, redaction, эгресс-контроль, тесты |
| Prompt injection | Страницы/письма/файлы | Taint, запрет повышения прав, подтверждение внешних действий |
| Накопление ошибок | Длинные задачи | Verifier по состоянию, перепланирование, лимиты |
| Стоимость | 94 инструмента, умная модель | Отбор инструментов, кэш, дешёвый исполнитель |
| Недоверие | Непонятно, что делает | Баннер, трасса, «почему», отмена, отчёт |
| Юридические/приватность | Снимки экрана, переписка | Хранение, срок, согласие, локальность |
