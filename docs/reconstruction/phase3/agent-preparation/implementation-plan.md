# Phase 3.4 — план внедрения (для DeepSeek)

Статус: план. Код не менять до этапа 0 и решений владельца.

Порядок этапов: 0 → 1 → 2 → 3 → 4 → 5 → 6. Этапы 1 и 3 частично независимы, но статус «Остановлено» (этап 3) нужен и в журнале (этап 1), поэтому их порядок фиксирован.

Общие правила для всех этапов:
- Миграции файлов журнала не делаем. Старые записи читаются тем же правилом, что новые.
- Новые IPC-вызовы: `ipcMain.handle` в `main.js`, метод в `preload.js`, заглушка в `renderer/dev-stub.js` для браузерной проверки.
- Новый файл в `src/` или `renderer/` — строка в карте `AGENTS.md` (тест `project-map.test.js`).
- Тексты окна — без названий моделей и поставщиков.
- Коммиты и `push` — только по просьбе владельца.
- Перед отчётом о готовности: `node --test` в `apps/jarvis-desktop` и `apps/nox-server`, проверка настоящим окном.

## Этап 1. Журнал: один источник статуса

**Цель:** окно и поиск показывают один и тот же статус для одной записи. Статус берётся из записи, которую написал цикл.

**Файлы:**
- `src/journal/status.js` (новый): `recordStatus(rec)` — единственная функция статуса. Вход: запись журнала. Выход: один из `confirmed`, `unverified`, `failed`, `refused`, `stopped`, `error`, `done`. Правило: сначала `rec.status`, если он есть; старые записи — по полям `decision`, `verified`, `ok`, `summary`.
- `src/journal/journal.js`: `historyStatus` делегирует в `recordStatus`. Добавить `stopped` (`resolution:'stop'`, `decision:'stop'`). Записи `decision:'resume'` и `decision:'stop'` (аварийный стоп) не считать «Выполнено».
- `main.js`: `readRecentJournal` — возвращает записи с полем `status` (совместимо: массив остаётся массивом, поля добавляются). Читает с учётом ротации (см. этап 2, пункт про чтение).
- `renderer/shared.js`: `statusOfRecord` оставить только как резерв для записей без `status`. Основной путь — статус из ядра.
- `src/agent/loop.js` (~700–735): в запись добавить `stopped: true` и `afterStop: true`, если результат пришёл после остановки. Изменение только добавляет поля.

**Ожидаемое поведение:**
- Рискованное действие без проверки (`status:'unverified'`) — «Не проверено» и в поиске, и в «последних».
- Шаг, прерванный стопом, — «Остановлено».
- Аварийный стоп — «Остановлено», не «Выполнено».
- Отказ — «Отклонено», провал проверки — «Провалено».

**Критерии приёмки:** AC-1.1 – AC-1.6.
**Риски:** R-01, R-02, R-18.
**Тесты:** T-N01, T-N02, T-N03, T-N04, T-N11; J-04, J-05, J-06, J-14, J-16, J-17.

## Этап 2. Фильтры, поиск, подробности

**Цель:** владелец находит нужную запись и понимает её, без догадок.

**Файлы:**
- `renderer/index.html`: `#statusFilter` — добавить «Выполнено» и «Остановлено». Новая разметка `#histDetail` (диалог подробностей) и блок ошибки загрузки с кнопкой «Повторить».
- `renderer/app.js`: раздел «Журнал» (~1417–1505). Ключ строки — `callId + runId + step`, не индекс. Поиск через `journal:search` с задержкой 250 мс и номером запроса: ответ устаревшего запроса отбрасывается. «Показать ещё» по `offset`. Счётчик «Показано N из M» — `M` берётся из ответа ядра.
- `renderer/nox-history.js` и `renderer/nox-history.css` (новые, если выбран этот вариант; иначе раздел в `app.js`). Стили — только токены темы.
- `src/journal/journal.js`: `searchJournal` — возвращать `total` (всего по фильтру) и `counts` по статусам (для подписей фильтров). Даты — по локальному дню.
- `main.js`: `journal:search` — передавать `source`; по умолчанию фильтр по текущему пространству (`workspaceId`); `journal:recent` тоже получает фильтр пространства. Чтение ротированной цепочки — с конца файла, без полного чтения синхронно (R-20).

**Подробности записи** (диалог `#histDetail`):
- время, инструмент (подпись из `TOOL_TITLES`), риск, решение, статус с объяснением словами, итог (`summary`), доказательство (`evidence`), маскированные аргументы, `runId`, шаг, `callId` (копируемые).
- Esc закрывает; фокус возвращается на строку.
- Без полного текста ввода: только «[скрыто, N симв.]».

**Ошибка загрузки:** сообщение «Не удалось загрузить журнал» и кнопка «Повторить». Если строки уже есть — они остаются, помечены «устарели», сообщение видно.

## Этап 3. Ход агента: честная остановка

**Цель:** окно не говорит «остановлено» раньше, чем ядро это подтвердило; строки не висят в «выполняется».

**Решение, которое нужно зафиксировать в начале этапа:** `done` с `cancelled` приходит сразу (как сейчас), а результат инструмента после остановки приходит отдельным событием `late_result`. Альтернатива — ждать завершения инструмента до `done` — задерживает кнопку «Стоп» на время инструмента. Рекомендуется первый вариант.

**Файлы:**
- `src/agent/loop.js`:
  - `stop()`: до `done` отправлять `status:'stopping'`; в `done` — `outcome:'stopped'`, `runningTool: {id, name, label}` (если инструмент ещё идёт).
  - `_emit`: после `_runClosed` разрешить только `late_result` (и `approval_closed`). Остальное — как сейчас.
  - Когда инструмент вернулся после остановки: `late_result` с `id`, `ok`, `summary`, `verified`; запись журнала — с `afterStop:true` (этап 1).
  - `checkEffect` после остановки: проверку выполнять и записывать, но в окно — только `late_result`.
- Инструменты без `signal` (R-15): в первую очередь `workspace.js` (чтение/запись), `observe.js`, `mail.js`, `missions.js`, `reminders.js`. Для каждого — либо проверка `signal` между шагами, либо явный текст «не прерывается, ждём завершения».
- `main.js`: `agent:stop` возвращает `{ok, state:'stopping'}`. Окно не пишет «Остановлено» по `ok`.
- `renderer/app.js`:
  - `stopTurn`: тост «Останавливаю…» и кнопка в состоянии ожидания до `done`.
  - `endTurn` / обработка `done`: незавершённые строки закрываются статусом «остановлено»; `late_result` обновляет строку, если она ещё на экране.
  - Итоговая строка: «Остановлено»; при `runningTool` — «ждём завершения „{label}“».
- `renderer/nox-screen.js` (~540): тон для «Остановлено» отдельно от «Готово».

**Критерии приёмки:** AC-3.1 – AC-3.7.
**Риски:** R-02, R-03, R-15, R-23, R-25.
**Тесты:** T-N05, T-N06; A-10, A-11, A-12, V-05.

## Этап 4. Подтверждения

**Цель:** решение владельца относится к одному конкретному действию; карточка не зависает; секреты не показываются открыто.

**Файлы:**
- `src/policy/approvals.js`:
  - `request`: уникальный `id` (сочетание `runId` и `callId`); при дубликате — событие `approval_closed` с `reason:'replaced'`, а не молчаливый отказ.
  - `respond`: `reason` всегда заполнен при `ok:false`.
  - Список ожидающих для окна: `pending()` — `id`, `name`, аргументы в маскированном виде, `autoCancelAt`.
- `src/agent/loop.js` `_askApproval`: `approval_request` несёт маскированные аргументы (`TYPED_TEXT_TOOLS` → «[скрыто, N симв.]»); полный текст — только по явному действию владельца в карточке, без сохранения.
- `main.js`: новый канал `approval:pending` (только чтение, только из главного окна). Вызывается окном при перезагрузке, чтобы восстановить карточку (R-09).
- `preload.js`: `pendingApprovals()`. `renderer/dev-stub.js`: заглушка.
- `renderer/shared.js` `call(name, args, opts)`: необязательный таймаут `opts.timeoutMs`; по умолчанию без таймаута, чтобы не менять остальные вызовы.
- `renderer/app.js` `answerApproval`:
  - таймаут ответа 8 с;
  - при сбое или таймауте карточка остаётся, кнопки снова активны, текст «Не удалось отправить решение. Попробуйте ещё раз»;
  - `A.busy` сбрасывается по таймауту;
  - `approval:respond` с `reason:'replaced'` — карточка закрывается с пояснением.
- `renderer/app.js` `showApproval`: `#apArgs` показывает маскированный текст (вопрос 1 решён владельцем); предпросмотр файла (`#apPreview`) ограничен по длине.

**Ожидаемое поведение:**
- «Разрешить» и «Отклонить» не дают двойного вызова.
- Сбой IPC не убирает карточку, пока ядро не подтвердило закрытие.
- После перезагрузки окна карточка восстанавливается из `approval:pending`, если запрос ещё ждёт.
- Ожидавший шаг не выполняется после перезапуска процесса (R-10).

**Критерии приёмки:** AC-4.1 – AC-4.7.
**Риски:** R-04, R-05, R-07, R-09, R-10, R-11, R-12, R-13, R-26, R-27.
**Тесты:** T-N07, T-N08, T-N09; A-05 – A-09, S-03, S-04, S-05, S-07 – S-12, S-19, S-20.

## Этап 5. Ошибки и завершение

**Цель:** после ошибки владелец понимает, что уже сделано, и не запускает действия второй раз.

**Файлы:**
- `renderer/app.js` `chatError` (~2133–2160) и кнопка «Повторить»:
  - если в ходе были выполненные действия (есть `tool_result` с `ok:true` или записи журнала с этим `runId`) — не повторять фразу автоматически;
  - показать: «Часть действий уже выполнена» со списком из журнала и кнопками «Открыть журнал» и «Продолжить с текущего места» (новый ход с пометкой, что уже сделано — вариант, который согласовать с владельцем, вопрос 3);
  - если ничего не выполнено — «Повторить» как сейчас.
- `src/agent/loop.js`: событие `error` несёт `message` без технических деталей и `runId`; причина — понятным текстом.
- `src/journal/journal.js` / `loop.js`: сбой записи журнала — событие `notice` с текстом «Шаг выполнен, но не записан в журнал» (R-19).
- Сводка хода: честный текст при `verification.confirmed === 0` (A-17).
- Тексты ошибок: без названий моделей и поставщиков (проверка `scrub`).

**Критерии приёмки:** AC-5.1 – AC-5.5.
**Риски:** R-06, R-08, R-19, R-29.
**Тесты:** T-N10; A-13, A-14, A-15, A-16, A-17, S-17.

## Сводка: изменения интерфейсов

| Канал или событие | Что меняется | Совместимость |
|---|---|---|
| `journal:recent` | Записи получают `status`; фильтр пространства | Массив сохраняется; поля добавляются |
| `journal:search` | Статусы `stopped`, `done`; `total`, `counts`; `source` | Старые фильтры работают |
| `agent:stop` | Ответ `{ok, state}` | Старое `{ok}` остаётся |
| `approval:pending` | Новый канал (чтение) | Новый |
| `approval:respond` | `reason` всегда при `ok:false` | Старые поля сохраняются |
| `agent:event` | Новые типы: `stopping`, `late_result`; `approval_closed.reason` (`replaced`, `timeout`, `stop`) | Старые типы не меняются |
| `done` | Поля `outcome:'stopped'`, `runningTool` | Старые поля сохраняются |
