## 1. Уникальность ID и связь с агентом, ходом и вызовом

**Исправлено для чата и агента экрана.**

- `Agent` получает свой `_agentId = randomUUID()` в конструкторе (`src/agent/loop.js:265`).
- `_askApproval` создаёт новый `approvalId = randomUUID()` на каждый запрос (`loop.js:843`). Ключом брокера служит именно он: `payload.id = approvalId` (`loop.js:855-868`). Исходный ID модели лежит отдельно в `callId`. Отмена при стопе отвечает по `approvalId` (`loop.js:877`).
- `ScreenAgent._askDanger` устроен так же (`src/screen/agent.js:151-172`).
- В брокере ID — ключ `Map`. Ответ находит ровно одно ожидание, решение возвращается в замыкание того вызова, который его создал. После `once` агент выполняет свой `call`. Подменить объект вызова можно только изнутри агента.

**Остатки:**

- Брокер по-прежнему молча заменяет ожидающий запрос с тем же ID (`src/policy/approvals.js:67`): старый получает `reject`, ответ на него применяется к новому. Чат больше не передаёт повторяющиеся ID, но защиты на уровне брокера нет. Исполнитель задач строит ID как `${taskId}:${call.id}` (`src/tasks/executor.js:1342`). Внутри одной задачи вызовы идут последовательно, поэтому одновременного совпадения я не нашёл. Если исполнитель начнёт выполнять вызовы параллельно, сбой ZM-001 вернётся в исходном виде. Тест `RESIDUAL` в `evidence/core/zm-core.test.js` фиксирует замену.
- Окно связывает строку действия в чате с запросом по `callId` (`renderer/app.js:2125-2139`). При одинаковом `callId` у двух агентов в одной карточке хода (например, параллельные рабочие роли из `src/tools/agents.js:112-118` пересылают свои события в общий чат) вторая строка не создаётся. Существующая строка сохраняет инструмент и аргументы первого действия, но кнопка «Решить» открывает запрос второго (`app.js:2139`). Отказ записывается в `C.rejected` по `callId` (`app.js:1635, 1732`) и может пометить чужую строку как отклонённую. Сам диалог показывает правильные данные, потому что берёт их из события в очереди. **Ошибка отображения найдена только чтением кода, живьём не воспроизводилась.**

## 2. Можно ли подтвердить другое действие

- Через совпадение ID — нет. Ядро: тесты ZM-001 в `evidence/core/`. Окно: S03 в двух вариантах и двух размерах.
- Ответ по старому ID вызова отклоняется ядром (core-тест `answering with the raw callId`).
- **Через смену первой карточки под курсором — да.** `answerApproval` читает текущую первую карточку очереди в момент обработки клика (`app.js:1708-1710`), а не ту, что была на экране при нажатии. Если в этот момент ядро закрывает показанный запрос A и окно сдвигает очередь на B, клик одобряет B. Ядро могло закрыть A по истечению 30 секунд, остановке или смене статуса задачи. Минимального времени показа или проверки «показано то, что подтверждено» нет. Воспроизведено живьём, подробности — `RACE-CONDITIONS.md`, раздел R1.
- Голосовой ответ «да» подтверждает первый запрос брокера `approvals.list()[0]` (`main.js:3401-3402`), а не карточку на экране. Обычно они совпадают. После перезагрузки окна, при карточке-призраке (`REGRESSION-FINDINGS.md`, N3) или после чужого `done` (N5) голос может подтвердить действие, которого на экране нет. **Найдено только чтением кода, голос живьём не проверялся.**

## 3. Повторные ответы и устаревшие запросы

- `_settle` удаляет запрос из `Map` до `resolve`. Второй ответ возвращает `false` (`approvals.js:159-166`). Двойной клик не создаёт второго эффекта: проверено в ядре и в окне (S05).
- Ответ после автоотмены возвращает `false` с причиной «время на подтверждение вышло» (`approvals.js:138-151`, S07).
- Ответ после отказа не одобряет следующий запрос того же вызова, потому что у повторного запроса новый `approvalId` (core-тест, S08).
- Решение `session` для одноразовых инструментов ядро понижает до `once` (`loop.js:658`). Окно здесь не решает: core-тест `forged "session"`.
- Неизвестное решение даёт `TypeError` в брокере (`approvals.js:90`), обработчик IPC отвечает `{ok:false}` (`main.js:3553`). Запрос остаётся в ожидании.
- Ответы принимаются только от главного окна (`fromWindow`, `main.js:1417-1419`). Мини-окно ответить не может.

## 4. Гонки, отмена при стопе, таймауты

- Если стоп пришёл после `once`, но до запуска, шлюз `loop.js:666-669` (`signal.aborted || _runClosed || _stopped()`) не даёт выполнить действие. Проверено core-тестом `Stop in the same tick`.
- Стоп во время ожидания вызывает `respond(approvalId,'reject')`. Агент при этом не отправляет `approval_closed`. В главном чате карточку убирает последующий `done` (`app.js:3132, 3139`). У рабочих ролей `done` в окно не пересылается (`src/tools/agents.js:112-118`). После разделения ID `tool_result` тоже больше не снимает карточку: `approvalDrop(ev.id)` с `ev.id = callId` (`app.js:3101`). Остаётся карточка-призрак (S15, `REGRESSION-FINDINGS.md`, N3).
- `done` любого агента вызывает `approvalClearChat()` и удаляет из окна все запросы, кроме запросов исполнителя задач (`app.js:1593-1599`). Запрос другого агента, который ядро всё ещё ждёт, исчезает с экрана (S16).
- Тайм-аут окна — 5 секунд (`app.js:1715-1718`). Тайм-аут ядра — 30 секунд (`approvals.js:9`, `main.js:668-672`). Остановить уже отправленный запрос IPC окно не может, но ядро принимает только первый ответ.

## 5. Потеря ответа IPC и синхронизация ядра с окном

- Новое событие `approval_closed` из `main.js:3546-3550` отправляется до возврата ответа IPC. Если ответ потерян, окно всё равно убирает решённый запрос (S11, S13, S14).
- **Побочный эффект:** если событие приходит, пока `A.busy === true`, `approvalDrop` перерисовывает следующий запрос с заблокированными кнопками (`app.js:1696`). После ответа IPC `approvalDrop(currentKey)` уже ничего не находит и не перерисовывает диалог (`app.js:1577-1580, 1735`). Кнопки следующего запроса остаются заблокированными (S04), см. `REGRESSION-FINDINGS.md`, N2.
- Если ядро ответило `ok:false` с причиной «запрос уже неактуален», окно оставляет карточку (`app.js:1724-1728`). Так задумано для временного сбоя связи. Но при окончательном отказе ядра карточка остаётся навсегда (S15).
- При `ok:false` или тайм-ауте окно пишет «Не удалось передать решение…», хотя ядро могло решение уже применить. В S11, S13 и S14 действие выполнилось, а окно сообщило об ошибке.
- После перезагрузки окна очередь пуста. Получить список ожидающих запросов окно не может: IPC для этого нет, а `state:get` не возвращает `approvals.list()`. Запрос невидим до автоотмены (S18). Это безопасно: само действие не выполняется.
