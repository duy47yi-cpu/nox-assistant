# Гонки

Все прогоны выполнены в настоящем окне Electron проекта (`main.js` целиком), в отдельном временном профиле. Действия фиктивные: агенты используют брокер приложения, а эффект — это запись в массив в памяти. Нажатия идут как настоящий ввод через `webContents.sendInputEvent` (mouseDown/mouseUp по координатам кнопки), а не `element.click()`. Стенд: `evidence/live/zm-live.js`, итоги: `evidence/live/runs/main-*-r3/summary.txt`.

## R1 — смена карточки под курсором: подтверждено действие, которого человек не видел · НОВОЕ, P0

**Сценарий S06.** Окно показывает запрос A, в очереди есть B («1 из 2»). Ядро закрывает A тем же путём, что и 30-секундный таймер: `broker._autoCancel(A)` → `onAutoCancel` → `approval_closed` в окно. Через 0, 40, 120 или 250 мс по тем же координатам приходит настоящее нажатие на «Разрешить».

| Прогон | Агенты пересылают `done` | Задержка | Итог |
|---|---|---:|---|
| 864×520 r3 | да (как главный чат) | 0 | **одобрен и выполнен B** |
| 864×520 r3 | нет (как рабочие роли) | 0 | безопасно: клик пришёл раньше события, ядро ответило «время вышло» |
| 864×520 r3 | нет | 40 / 120 / 250 | **одобрен и выполнен B** |
| 1200×720 r3 | да | 0 | **одобрен и выполнен B** |
| 1200×720 r3 | нет | 0 / 40 / 120 / 250 | **одобрен и выполнен B** |
| 864×520 r2 | нет | 0 / 40 / 120 / 250 | **одобрен и выполнен B** (все четыре) |

Итого в r2 и r3 B выполнился в 13 случаях из 14. На снимке перед нажатием видны A, «1 из 2» и `current` = ID запроса A. В IPC ушёл ID запроса B, выполнился эффект `ZM-SWAP-B-…`.

**Почему.** `answerApproval` берёт `A.queue[0]` в момент обработки клика (`renderer/app.js:1708-1710`). Связи с тем, что было отрисовано при нажатии, нет. Задержки после смены содержимого тоже нет. Позиции кнопок у A и B совпадают. При задержке 0 мс B, вероятно, ещё даже не был отрисован. При 250 мс B на экране меньше времени обычной реакции человека.

**Условия.** Одновременно ждут два запроса: исполнитель задач и чат, чат пространства и главный чат или параллельные рабочие роли. Показанный запрос закрывается ядром в момент нажатия: истечение 30 секунд, когда человек жмёт на последней секунде отсчёта, остановка, смена статуса задачи. Условие похоже на ZM-001: два источника запросов и нажатие в узком окне времени. Последствие то же: выполняется не то действие, которое видел владелец.

**Повтор:** из `apps/jarvis-desktop` выполнить `node_modules/.bin/electron ../../docs/audits/zero-mercy/independent-s0/evidence/live/zm-live.js main 1200x720 <новое-имя>`. Смотреть результаты `S06-*`.

## R2 — совпавший ID и нажатие в момент прихода второго запроса (ZM-001) · исправлено

S03, два варианта: клик синхронно с событием B и клик сразу после события B. Оба агента отправили `callId = "call_0"`. Ядро выдало разные `approvalId`, окно показывало A, выполнился только A. Результат одинаков на 864×520 и 1200×720. В ядре то же проверено с тремя агентами и с обратным порядком доставки (`evidence/core/zm-core.test.js`).

## R3 — двойное нажатие «Разрешить», B в очереди · безопасно, но только из-за N2

S05: два настоящих нажатия с разницей 60 мс. Выполнился A один раз, B не выполнялся. Второе нажатие не прошло, потому что кнопки B заблокированы ошибкой N2 (`REGRESSION-FINDINGS.md`). Если исправить N2 без защитной задержки, двойной клик станет повторением R1.

## R4 — «видно A, B уже в очереди», позднее нажатие · привязка верна, следующий запрос заблокирован

S04: через 0,5 с после появления B нажатие на «Разрешить» выполнило A. Это правильно. Затем диалог показал B, но все три кнопки остались `disabled`. Нажатие на «Разрешить» B ничего не сделало, сработал только Escape. Воспроизводится на обоих размерах. Подробности — N2.

## R5 — отказ и сразу новый запрос с тем же ID вызова · исправлено

S08: «Отклонить», модель повторяет `call_0`, приходит новый запрос с новым `approvalId`. Ответ по старому ID через IPC вернул `ok:false`. «Разрешить» на новом запросе выполнило действие один раз.

## R6 — стоп во время ожидания и сразу после «Разрешить» · исправлено

- S09: `agent.stop()` при открытом диалоге закрыл диалог. Позднее нажатие и прямой IPC вернули `ok:false`, эффекта нет.
- Core-тест: `respond(once)` и `stop()` в одном такте. Шлюз `loop.js:664-669` не дал выполнить действие.

## R7 — `done` одного агента убирает запрос другого · НОВОЕ наблюдение, P2

S16: при открытом запросе агента X в окно пришёл `done` другого хода. Диалог закрылся, счётчик стал 0, а ядро продолжало ждать X. Удаляет `approvalClearChat` (`app.js:1593-1599, 3132, 3139`). Это ошибка рассинхронизации: действие само не выполнится, через 30 секунд его отменит таймер. Но владелец его не видит, а голосовое «да» его подтвердит (`main.js:3401`). Ошибка в коде появилась до исправления Codex, но мешает проверке ZM-018.
