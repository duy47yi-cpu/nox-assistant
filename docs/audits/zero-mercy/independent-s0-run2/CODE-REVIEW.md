## Цепочка

Agent → ApprovalBroker → IPC → окно → решение → IPC → брокер → агент.

1. `src/agent/loop.js:652-655` — политика вернула `ask`, вызывается `_askApproval`.
2. `src/agent/loop.js:843` — ключ разрешения `approvalId = randomUUID()`, отдельно от `callId` модели (`:842`). В событии ещё `agentId` (`:265`, случайный на экземпляр) и `runId`.
3. `src/agent/loop.js:875` — запрос регистрируется в брокере **до** события в окно (`:880`), быстрый ответ не теряется.
4. `src/agent/loop.js:877-879` — отмена хода (`signal`) отклоняет именно этот `approvalId`.
5. `main.js:3534-3553` — `approval:respond`: только из своего окна (`fromWindow`), брокер решает по id, неверное решение даёт `TypeError` → `{ok:false}`. При успехе ядро шлёт окну `approval_closed` **до** ответа IPC (`:3546`) — сверка очереди при потере ответа.
6. `renderer/app.js:1707-1736` — `answerApproval` фиксирует `currentKey = A.queue[0].id` в момент нажатия, блокирует кнопки (`A.busy`), ждёт ответ ядра не больше 5 с; при неуспехе запрос остаётся, кнопки снова доступны.
7. `src/agent/loop.js:658-669` — после ответа: `session` для одноразовых инструментов понижается до `once`; если пока ждали пришёл стоп/отмена/закрытие хода — действие не выполняется (`resolution='stop'`).
8. Агент экрана: `src/screen/agent.js:148-186` тот же механизм со случайным ключом; опасный шаг спрашивается всегда, даже при одобрении «на сессию» (`:127-131`).

## Найденные слабые места

- **R2-01 (P1, остаток ZM-001 вне исправленных файлов).** `src/tasks/executor.js:1342`: id подтверждения исполнителя = `taskId:` + id вызова модели. Если модель повторяет id (именно корень ZM-001), второй запрос получает тот же ключ. Брокер в `request()` (`approvals.js:67-68`) тихо отклоняет ждущий запрос с этим id и стирает причину закрытия; ответ, отправленный на старую карточку, принимается новым действием. Воспроизведено на брокере (`evidence/adversarial.test.js`, тесты R2-01, R2-01b). На живом исполнителе (мандат, песочница) **не воспроизводил** — нужен ход исполнителя с инструментом `requiresApproval`.
- **R2-02 (P2).** Голосовое «да» (`main.js:3401`) отвечает на `approvals.list()[0]` — самый старый запрос в брокере. Окно показывает `A.queue[0]`, а кнопка «Решить» (`app.js:1601-1605`) переставляет выбранный запрос вперёд. Владелец видит B, говорит «да» — одобряется A. Порядок брокера подтверждён тестом R2-02; в окне голосом **не проверял** (нужна диктовка).
- **R2-03 (P2, интерфейс).** Строка действия в чате связана по сырому `callId` (`app.js:2125`). При повторе id второй запрос переиспользует строку первого: текст остаётся от A (`W1-A.txt`), статус «ждёт решения» и кнопка «Решить» ведут к B. Видно на снимках `evidence/shot-main-*-W1-dialog-B.png`. Сам диалог показывает B правильно, поэтому выполнения чужого действия нет, но строка вводит в заблуждение.
- **R2-04 (P3).** После перезагрузки окна (renderer) ожидающая карточка не восстанавливается: канала «дай список ожидающих» нет. Ядро ждёт до автоотмены 30 с, действие не выполняется. Проверено в окне (W8).
- **R2-05 (P3).** Если ядро ответило «запрос уже неактуален», окно оставляет карточку (`app.js:1722-1728`) и полагается только на событие `approval_closed`. Если и оно потеряно, карточка висит до конца хода чата (`approvalClearChat`, `app.js:1593`); для запросов исполнителя — до смены статуса задачи. Только по коду, в окне не воспроизводил.
- Мелочь: `src/tasks/runtime.js:524` — id возобновления `resume:<id>:<мс>`; два возобновления одной задачи в одну миллисекунду совпадут. Практически недостижимо.
