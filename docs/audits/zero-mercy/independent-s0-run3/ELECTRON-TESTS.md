# Настоящее окно Electron — прогон 3

Electron 44.9.3 здесь запускается (`ENVIRONMENT-DIAGNOSTICS.md`). Все проверки — в настоящем окне `main.js` без изменений кода, во временном профиле `%TEMP%\zm-run3-*`, настройки `mode: ask`. Модель — фиктивный сервер на 127.0.0.1, ключ-заглушка. «Действие» — `workspace_write` во временную рабочую папку. Уведомления Windows в стенде отключены. Реальных данных, системных действий и платных вызовов нет.

Нажатия — настоящие события мыши и клавиатуры (`sendInputEvent`), а не `element.click()`.

## Стенд прогона 3: `evidence/window-harness-run3.js`

Запуск из `apps/jarvis-desktop`:

```
node_modules/electron/dist/electron.exe ../../docs/audits/zero-mercy/independent-s0-run3/evidence/window-harness-run3.js --size 1200x720
```

Второй одновременный запрос создаётся в **настоящем** брокере `main.js`. Стенд подменяет класс `ApprovalBroker` подклассом, который только запоминает экземпляр. Окну запрос приходит тем же событием `approval_request`, отвечает окно через настоящий `approval:respond`. Фиктивен только агент, который этот запрос породил. Обёртка `approval:respond` только записывает вызовы.

Результаты: `evidence/window-run3-1200x720.json`, `evidence/window-run3-864x520.json`, вывод `evidence/window-run3-*-stdout.txt`, снимки `evidence/shot-<размер>-<сценарий>.png`.

| ID | Сценарий | 1200×720 | 864×520 |
|---|---|---|---|
| R1 | Ожидающий запрос → перезагрузка окна → карточка с тем же id вернулась → «Разрешить» мышью → выполнено только R1-A | **PASS** | **PASS** |
| R2 | Модель шлёт `call_0` дважды за ход: две раздельные строки действий (A «подтверждено», B «ждёт решения» с кнопкой «Решить»), диалог B, Escape → выполнено только A | **PASS** | **PASS** |
| R3 | Два запроса одновременно (чат A + задача B), диалог остаётся на A («1 из 2»), «Разрешить» у A мышью → показан B | PASS по безопасности (выполнено только A, B отклонён) | то же |
| R3, кнопки B | После ответа на A кнопки B выключены, «Отклонить» мышью не срабатывает, работает только Escape | **FAIL** (R3-02) в последнем прогоне; в двух ранних прогонах кнопки были включены | **FAIL** (R3-02) |
| R4 | A истекает (автоотмена 30 с), B задачи (без «На сессию») встаёт в диалог; клик «Разрешить», нацеленный на A, через 62–63 мс | PASS: кнопки сдвинулись, клик попал в фон диалога, B не одобрен. Защитой это не является | PASS (так же) |
| R4c | То же, но B того же вида, что A (второй агент, та же раскладка); клик через 53–63 мс после истечения A | **FAIL**: под курсором `data-decision="once"`, ядро получило `once` для id B, **B одобрен** | **FAIL**: так же, 53 мс |
| R5 | Ядро сняло запрос задачи, событие `approval_closed` потеряно; «Разрешить», затем Escape | PASS по безопасности (ничего не выполнено); карточка висит после обоих нажатий, исчезает только после перезагрузки (R3-03) | то же |

Как получен FAIL в R4c: A показан как «1 из 2» с отсчётом «Без ответа отменится через 1 секунду» (`shot-*-R4c-A-before-expiry.png`). Через 60 мс после автоотмены A приходит клик мышью в точку кнопки «Разрешить», снятую, пока был виден A. К этому моменту диалог уже показывает B, и брокер принимает `once` для B (`ipcForB: ["once"]`, `bDecisionByClick: "once"`). Время клика задано скриптом. Человеку с реакцией 150–300 мс хватит чуть более раннего движения: окно подмены сопоставимо с одним нажатием.

Ошибки стенда, найденные по ходу (честно): в первых вариантах R4 второй запрос создавался почти одновременно с первым, и его собственная автоотмена закрывала диалог раньше клика. Такие прогоны не засчитаны. В засчитанном варианте B появляется через 10 с после A.
