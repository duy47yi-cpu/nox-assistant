# Архитектура подключения реального звука и ASR для Nox C7 (Этап 2)

Этот документ описывает переход от изолированного синтетического прототипа `apps/nox-meeting-spike/` к реальному захвату звука в Windows и потоковому распознаванию речи. **Ни один из перечисленных пакетов или бинарных модулей сейчас не установлен** и требует явного согласия владельца перед началом второго этапа.

---

## 1. Архитектура подключения реального аудио

Существующее ядро C7 уже разделено по контрактам:

```text
[Windows Audio Sources]                      [Nox C7 Core Engine (уже реализован)]
  ├─ WASAPI System Loopback ──┐
  │   (голоса собеседников)    │  Named Pipe / stdout / Worklet
  │                            ├──► Resampler (48kHz→16kHz mono s16le) + Silero VAD
  └─ Microphone Capture ───────┘         │
      (голос владельца)                  ▼
                                RealAudioStreamAdapter (реализует AudioStreamAdapter)
                                         │
                                         ▼ (AudioChunk)
                                PrivacyController (явное согласие + запрет лишней записи)
                                         │
                                         ▼
                                BackpressureQueue (жёсткий потолок очереди и RAM)
                                         │
                                         ▼
                                RealASRProvider (реализует ASRProvider)
                                  ├─ partials ─► TranscriptAssembler (дедуп, поздние ответы,
                                  └─ finals   ─►   починка битых временных меток)
                                                       │
                                                       ▼
                                                 SpeakerTimeline (честные канальные метки)
                                                       │
                                                       ▼
                                                 MeetingSummaryGenerator (конспект)
```

### Почему важно разделять два канала (Loopback + Microphone)

1. **Половина диаризации «бесплатно»:** поток `microphone` однозначно принадлежит локальному пользователю, а `system_loopback` — удалённым участникам созвона.
2. **Эхо и перекрёстная запись:** если пользователь сидит без наушников, звук собеседников из динамиков попадает в микрофон. На этапе 2 понадобится либо системный Acoustic Echo Cancellation (Windows Voice Capture / WebRTC AEC3), либо кросс-корреляционное подавление между двумя каналами до отправки в ASR.
3. **Устойчивость к смене устройств:** при переключении Bluetooth-гарнитуры посреди созвона WASAPI-адаптер должен ловить `IMMNotificationClient` (`OnDefaultDeviceChanged`) и переподключать поток без остановки `SessionManager`.

## 2. Варианты захвата звука на Windows (WASAPI Loopback)

| Вариант | Как работает | Лицензия | Размер установки | Зависимости | Плюсы и минусы |
|---|---|---|---|---|---|
| **1. Electron `setDisplayMediaRequestHandler({ audio: 'loopback' })` + `getUserMedia`** | Встроенный Chromium/Electron API; `AudioWorklet` ресемплирует в 16kHz PCM | Входит в Electron (MIT) | **0 МБ доп. пакетов** | Нет (уже в приложении) | + Нулевые внешние зависимости.<br>− Требует запрашивать `video` вместе с `audio` (видеокадры нужно сразу отбрасывать); захватывает весь системный микс без лёгкого выбора отдельного процесса (`Zoom.exe` / `Teams.exe`). |
| **2. Rust-хелпер на `cpal` / `windows-rs` (WASAPI)** | Отдельный компактный `.exe` или N-API аддон; шлёт PCM по Named Pipe / `stdout` | MIT / Apache-2.0 (`cpal`, `windows-rs`) | **~1.5–3 МБ** (статический `.exe`) | Только системные DLL Windows 10/11 | + Нативный WASAPI, поддержка per-process loopback на Win 10 20348+ / Win 11, нет привязки к захвату экрана.<br>− Нужна сборка Rust-бинарника и подпись/упаковка в `extraResources`. |
| **3. .NET хелпер на `NAudio` (`WasapiLoopbackCapture`)** | Консольный процесс C# (`.exe`), передаёт PCM по `stdout`/pipe | MIT (`NAudio`) | **~15–30 МБ** (self-contained .NET 8) или **~1 МБ** (если .NET Desktop Runtime уже в системе) | .NET runtime либо self-contained сборка | + Проверенный зрелый API на Windows.<br>− Существенно тяжелее по весу инсталлятора, чем Rust/C++ при self-contained сборке. |
| **4. Нативный C++ / WinRT / WASAPI N-API модуль** | Прямой вызов `IAudioClient` / `ActivateAudioInterfaceAsync` | Свой код (Apache-2.0) | **< 1 МБ** | VC++ Redistributable (обычно уже есть у Electron) | + Минимальный вес и минимальная задержка.<br>− Дороже в сопровождении, требует C++ toolchain (MSVC) при сборке. |

**Рекомендация для Nox:**
- Для быстрого пилота с минимальными зависимостями проверить вариант 1 (встроенный Electron loopback).
- Для надёжного коммерческого продукта без побочных эффектов захвата экрана и с поддержкой захвата конкретного процесса/обработки смены наушников — **компактный нативный Rust WASAPI-хелпер (~2 МБ)** или минимальный C++ N-API/хелпер.

## 3. Анализ реальных ASR-провайдеров

|---|---|---|---|---|---|---|---|

| **`faster-whisper` (CTranslate2)** | **MIT** (`faster-whisper` и `CTranslate2` — MIT; веса Whisper — MIT) | Python/CTranslate2 связка **~250–450 МБ** (CPU) или **~1.5–3+ ГБ** (с CUDA/cuDNN) + модель (`small` int8 ~160 МБ, `large-v3` int8 ~1 ГБ) | VC++ Redistributable; для GPU — **NVIDIA CUDA 12 + cuDNN 9** | CPU: выше `sherpa-onnx`; **NVIDIA GPU: очень быстро** и высокоточно | **Псевдо-потоковая** (через VAD + chunking, напр. ### Практический вывод по выбору стека для Nox (без ручного Python)

1. **Лучший кандидат для живых субтитров (real-time partial + low CPU):**
   `sherpa-onnx` (потоковый Zipformer для русского, ~70–100 МБ) + `Silero VAD` (~2 МБ, MIT).
   Работает на обычном ноутбуке без дискретной GPU, без Python, с честными потоковыми субтитрами за сотни миллисекунд.
2. **Опциональный «качественный проход» после созвона (или на мощном ПК/GPU):**
   `whisper.cpp` (MIT, Vulkan + CPU, без Python) поверх сохранённых речевых сегментов после окончания звонка — даёт лучшее качество пунктуации и редких терминов при минимальных зависимостях.
3. **Почему `faster-whisper` проигрывает по упаковке на Windows:**
   `faster-whisper` сам по себе завязан на Python, а GPU-ускорение тянет связку CUDA/cuDNN (~1.5–3 ГБ). Если нужен именно CTranslate2, для десктопа разумнее либо C++ обёртка над `CTranslate2`, либо `whisper.cpp` с Vulkan (работает и на AMD/Intel/NVIDIA без установки CUDA SDK).

### Как доставлять пользователю без ручной настройки Python

1. **Никакого `pip` и системного Python:** сам движок (например, `sherpa-onnx` / `whisper-server.exe` + `wasapi-helper.exe`) кладётся в `extraResources` установщика NSIS (уже настроенного в `apps/jarvis-desktop/package.json`).
2. **Модели скачиваются только по явному действию пользователя** в отдельную локальную папку данных (не в основной код), с проверкой SHA-256 и понятным прогрессом размера («Скачать пакет распознавания созвонов: ~95 МБ»).
3. **Аппаратное определение при первом запуске:** проверка наличия AVX2/GPU (Vulkan) и автоматический подбор квантизованной модели (`int8`).

## 4. Оценка задержек и системных требований

### Что уже измерено в прототипе C7 (синтетический прогон 1000 фрагментов)

Замеры выполнены скриптом `scripts/benchmark-latency.js` на синтетических буферах (без реального аудио и без нейросети распознавания):

- **Ingest + валидация + BackpressureQueue:** `p50 ~ 0.0005 мс`, `p95 ~ 0.001 мс`, `max < 0.15 мс`.
- **TranscriptAssembler + SpeakerTimeline:** `p50 ~ 0.01 мс`, `p95 ~ 0.04 мс`, `max ~ 1 мс`.
- **Генерация детерминированного конспекта (40 финальных сегментов):** `~0.2–14 мс` (на холодном/разогретом V8).
- **Собственный накладной расход конвейера C7 — менее 1–2 мс на фрагмент.**

### Реалистичный бюджет задержек на этапе 2 (ориентир, не замер)

- Захват WASAPI + ресемплинг 48k→16k + буфер фрейма: **20–60 мс**
- Локальный Silero VAD: **5–20 мс**
- Передача в локальный worker/IPC: **1–5 мс**
- **Реальное время инференса ASR (основная задержка!):**
  - Streaming Zipformer (`sherpa-onnx` CPU): **150–400 мс** на partial, **400–800 мс** на финал.
  - Chunked Whisper (`whisper.cpp` `small` CPU / Vulkan): **600–2500 мс** в зависимости от длины окна и GPU.
- **Итог:** с `sherpa-onnx` живые субтитры укладываются в **~0.3–0.8 с** на среднем ноутбуке.

### Минимальные и рекомендуемые требования к ПК

- **Минимум (streaming CPU):** Windows 10/11 x64, CPU с AVX2 (4 ядра), 8 ГБ RAM, ~300 МБ свободного места (для бинарников и малой streaming-модели).
- **Рекомендуется (streaming + постобработка/конспект):** Windows 10/11 x64, 6+ ядер CPU, 16 ГБ RAM, опционально GPU с Vulkan (6+ ГБ VRAM для крупных моделей `whisper.cpp` или локального LLM-конспекта).

## 5. Список зависимостей, требующих разрешения владельца перед Этапом 2

На текущем этапе **ничего не установлено**. Для перехода к реальному захвату и распознаванию потребуется одобрение на конкретный набор из списка:

1. **Захват системного звука и микрофона на Windows (выбрать 1 вариант):**
   - Вариант A: Встроенный Electron `setDisplayMediaRequestHandler` (0 новых пакетов, но есть ограничения на per-process capture и обязателен запрос video track).
   - Вариант B (рекомендуется): Нативный WASAPI helper на базе **Rust `cpal` + `windows-rs`** (MIT / Apache-2.0, ~2 МБ бинарник) либо **`.NET NAudio`** (MIT).
2. **Локальный VAD (определение границ речи и тишины):**
   - **Silero VAD** (ONNX, MIT, ~2 МБ) — для отсечения тишины до ASR и экономии CPU.
3. **Локальный потоковый ASR (выбрать 1 основной + опционально 1 для постобработки):**
   - **Вариант 1 (рекомендуется для live-субтитров):** `sherpa-onnx` (`sherpa-onnx-node` или sidecar C++ binary, Apache-2.0) + потоковая русская модель Zipformer (~70–100 МБ).
   - **Вариант 2 (высокая точность оффлайн/пост-прохода):** `whisper.cpp` (MIT, Vulkan/CPU бинарник) + квантизованная модель Whisper (`small`/`medium`).
   - **Вариант 3 (только если нужен Python/CUDA):** `faster-whisper` + `CTranslate2` (MIT).
4. **Опциональная диаризация удалённого канала (Этап 3):**
   - Локальные speaker embeddings (`sherpa-onnx` speaker identification / `wespeaker`, Apache-2.0) — только для кластеризации «Собеседник 1 / 2» внутри канала созвона без угадывания реальных имён.

## 6. Честный перечень ограничений текущего прототипа

1. **Нет реального захвата звука:** микрофон и WASAPI loopback не подключены и принудительно заблокированы в `PrivacyController`.
2. **Нет реального распознавания речи (ASR):** `SyntheticASRProvider` генерирует заранее заданные или шаблонные тексты по синтетическим фрагментам и служит только для проверки архитектуры, сбоев, задержек и сборки текста.
3. **Упрощённый конспект (`MeetingSummaryGenerator`):** извлечение решений, задач и вопросов работает детерминированно по ключевым фразам/вопросительным знакам, без смыслового пересказа через LLM. Для глубокой смысловой суммаризации на этапе 2 нужно подключить провайдер к «Умной/Быстрой» модели Nox (с явным уведомлением о передаче текста, если модель облачная).
4. **Нет акустической диаризации внутри одного канала:** если в `system_loopback` говорят два разных удалённых собеседника и провайдер не передаёт `speakerHint` (кластер), прототип честно покажет единую канальную метку `Собеседник (удалённый канал, личность не определена)`.
5. **Нет подавления акустического эха (AEC):** без наушников звук из динамиков может дублироваться между каналом loopback и микрофоном до внедрения AEC на этапе 2.
6. **Нет автоопределения активного звонка (Zoom/Meet/Teams):** старт и остановка в прототипе выполняются только вручную с явным согласием.
7. **Не интегрировано в основное окно Electron `apps/jarvis-desktop`:** весь код и UI полностью изолированы в `apps/nox-meeting-spike/`.
